# Последовательности поведения

Источник: [Behaviour Tasks](https://the-official-worldbox-wiki.fandom.com/wiki/Behaviour_Tasks); редакция `23176`, дата `2026-10-19T21:23:58Z`. План подготовлен по полному тексту этой редакции.

## Что подтверждает источник

Behaviour Tasks описывает цепочки действий, выбираемых работой или решением существа. random_move ищет точку и ждёт 1–6 секунд; farmer_random_move ждёт 1–3. fight повторно проверяет допустимость цели; move_from_block ищет безопасную границу области; swim_to_island ищет сушу. В тексте заявлено 117 задач, но таблица неполная и большинство строк To be done. Dreamwalking описан подробнее: взрослый носитель Dreamweavers воздействует на спящего и отдельно пытается изменить культуру/язык/религию.

Оговорки: Источник WIP и прямо предупреждает о неточности. Заявленные 117 не равны числу полностью описанных задач; недостающие правила проектировать явно, не приписывать оригиналу.

## Наша отправная точка

`src/systems/people.ts`, `navigation.ts`, `economy.ts`, `construction.ts` уже исполняют маршруты и действия. Их нельзя заменить списком названий из незавершённой wiki. Задача этого плана — сделать существующие цепочки понятными, прерываемыми и расширяемыми.

## Взаимодействия и результат

- Решение выбрало добычу → цепочка находит залежь, идёт, добывает, несёт и разгружает → результат меняет запас только на последнем шаге.
- Цель боя исчезла → guard шага отклоняет атаку → выбирается новое допустимое действие.
- Существо оказалось в воде → аварийная цепочка ищет безопасный берег → обычная работа возобновляется после выхода.
- Dreamweaver завершил собственное действие → проверяется спящий получатель → каждый социальный эффект выполняется отдельно.

Ниже описывается предлагаемая реализация Pocket Overlord. Числа из исходной статьи служат отдельным ориентиром, а переносимые ограничения проверяются на масштабе нашего мира. Не объявлять одинаковыми понятия только из-за похожего имени: принадлежность, выполняемое действие и временное состояние должны сохранять собственный смысл.

## Работы

1. Описать TaskDefinition как список стадий с canStart/canContinue/complete/cancel, без сохранения функций в snapshot.
2. Первым проходом перенести существующие добычу, доставку, стройку, еду, бой и аварийное плавание; сохранить порядок систем и поведение.
3. Добавить устойчивый stageId, прогресс, targetId и retryAt; невозможный маршрут должен возвращать управляемую отмену.
4. Каталог исходных task IDs сгруппировать по передвижению, гражданству, производству, армии, транспорту, специальным существам и ожиданию; строки без правил не считать реализованными.
5. Подключить новые конкретные цепочки из планов элементов только когда существует их источник и наблюдаемый результат.
6. В инспекторе показывать человеческое действие и этап, сохранив служебные ID только в диагностике.

На каждом переходе обновлять данные владельца и связанные ссылки вместе; промежуточное состояние не должно давать повторную награду или оставлять участника одновременно в несовместимых состояниях. Для игрока показать действующую причину, участника и наблюдаемое следствие, а не служебный идентификатор. Обновлять текст через `src/i18n.ts`; существующие действия жителей и доступные команды должны продолжать работать.

## Зависимости и границы

Обязательные: существующая симуляция, реестр сущностей и сохранения; новые соседние системы для базовой части не требуются.

Будущие интеграции: [Neurons](neurons.md), [Unit Tasks](unit-tasks.md), [Jobs](jobs.md), [Subspecies Traits](subspecies-traits.md).

## Приёмка

- Добыча не идёт до достижения залежи.
- Прерванная доставка продолжается с тем же грузом.
- Удалённая цель боя не получает урон.
- Повторный запуск ожидания не сбрасывает таймер бесконечно.
- Задача без подтверждённых правил не выдаёт фиктивный успешный результат.
- Сохранение в середине активного перехода и продолжение после загрузки дают тот же результат и расход случайности, что непрерывная симуляция; пауза не двигает таймеры.
- Удаление участника, владельца или цели не оставляет ошибочных ссылок; недоступность пути не считается успешным действием. Если механика не требует перемещения, проверять доступность объекта через его жизненный цикл.

Проверить актуальные валидаторы `src/content/components.ts` и `src/persistence/schema.ts`, добавить миграцию только при необходимости формата. Выполнить относящиеся модульные проверки и реальную проверку отображаемого результата, затем сборку.
